# From the lab to production

> What companies run instead of each lab piece, and where certificates fit next to the other auth labs.

## 1. Every lab piece and its production counterpart

| Lab | Production (typical) |
|---|---|
| `pki/pki.sh` with a CA key on disk | **Mesh CA** (Istio `istiod`, Linkerd identity) or **SPIRE server**, backed by a **cloud CA/KMS/HSM** (AWS Private CA, Google CAS, Vault PKI). Offline root → intermediate → workload certificates |
| `issue <name>` by hand | **Automatic issuance per workload**: the mesh reads the Kubernetes service account (or SPIRE attests the node and process) and issues `spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>` |
| 24 h lifetime, `rotate` command | **Minutes to hours** (Istio's default is 24 h, often shorter), rotated **automatically** before expiry |
| Envoy restart to load new files | **SDS (Secret Discovery Service)**: the control plane streams new certificates to Envoy, with **no restart and no dropped connections** |
| CRL file, 30 days | Mostly **short lifetimes instead of revocation** ("let it expire"). Where revocation matters: OCSP or CRLs distributed automatically, or removing the workload's registration (SPIRE) |
| `envoy/*.yaml` written by hand | **Generated by the mesh control plane** from Kubernetes services and policies |
| `require_caller(...)` in each app | **Mesh authorization policies** (Istio `AuthorizationPolicy`, Linkerd `AuthorizationPolicy`, Envoy RBAC) enforced in the sidecar, and/or app-level checks like the lab's for business rules |
| `forward_client_cert_details: SANITIZE_SET` | The same Envoy feature; Istio enables it by default |
| Sidecar per app (`network_mode: service:…`) | Sidecar container in each **Kubernetes pod**, injected automatically. Or **sidecar-less**: Istio ambient (ztunnel per node), Cilium |
| Ports published for the host | An **ingress/API gateway** terminates external TLS (or mTLS for partners), then the mesh carries mTLS inside the cluster |

**Istio, for example**, gives you this lab with two settings: sidecar injection on the namespace, and `PeerAuthentication` with `mtls.mode: STRICT`. Every service then gets an identity, a certificate, rotation and mTLS without any code or certificate files.

## 2. Where certificates are used for authentication, and where they aren't

| Use | Common in industry? | Lab |
|---|---|---|
| **Service ↔ service inside the platform** | **Yes, the standard** (zero-trust / service mesh) | this lab |
| **Partner / B2B APIs** (a bank's API to a fintech, IoT devices) | **Yes**: API gateways offer mTLS (AWS API Gateway, Cloudflare, Apigee, Kong), often combined with OAuth (certificate-bound tokens, RFC 8705) | this lab's pattern, at the gateway |
| **Company devices** (managed laptops and phones) | **Yes**: MDM installs a device certificate; zero-trust access proxies (Google BeyondCorp, Cloudflare Access, Zscaler) require it | — |
| **People logging in** | Mostly **no**: SSO with passwords + MFA, passkeys/FIDO2. **Except** smart cards (PIV/CAC) in government, defence and banking, via the identity provider (Entra ID certificate-based auth, Keycloak X.509) | the other labs (Keycloak); smart-card style login is Keycloak's X.509 authenticator |

## 3. Combining with the other labs

A realistic system uses **both**:
- **people** sign in through an identity provider (`keycloak-jwt-python` / `oauth2-bff-python`) and their requests carry a JWT or session;
- **services** talk to each other over mesh mTLS (this lab), proving *which service* is calling;
- when a downstream service also needs to know *which user* a request is for, the user's token is forwarded or exchanged (OAuth token exchange, RFC 8693) **on top of** the mTLS connection.

## 4. Checklist before anything real

- [ ] Root CA offline, intermediate CA in KMS/HSM, the workload CA rotated on a schedule.
- [ ] Automatic issuance tied to a real workload identity (Kubernetes service account, SPIRE attestation), never "anyone who can run the issue script".
- [ ] Certificates in memory (SDS), lifetimes measured in hours, renewal alarms.
- [ ] Default-deny authorization policies; allow-lists per route, like the lab's table.
- [ ] Apps unreachable except through the proxy (network policies), so trusting identity headers stays safe.
- [ ] Monitoring: handshake failures (`ssl.fail_verify_*`), certificate expiry, CA health.
